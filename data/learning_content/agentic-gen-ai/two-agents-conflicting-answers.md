## Question

**Two agents produce conflicting answers. Who decides which answer is correct?**

## Short Answer

**The orchestrator should not blindly choose one agent.**

A production system should have a **validation/evaluation layer** that compares the agents' answers against trusted evidence, business rules, confidence signals, and the task's evaluation criteria.

```text id="conflict01"
                 User Request
                      |
                      v
                Orchestrator
                 /        \
                v          v
           Agent A      Agent B
                |          |
                +----+-----+
                     |
                     v
             Evaluation Layer
          /        |         \
       Evidence  Rules     Judge
          |        |         |
          +--------+---------+
                     |
              +------+------+
              |             |
          Confident      Uncertain
              |             |
              v             v
          Final Answer    Human Review
```

The important principle is:

> **The LLM should generate candidate answers; an independent evaluation layer should determine whether the answer is acceptable.**

NIST's current work on agent evaluation similarly emphasizes independent evaluation probes, trusted reference material, structured verdicts, and audit trails rather than simply trusting an agent's output. :chatgpt-content-reference{index="0"}

---

# 1. First Question: Why Are They Conflicting?

Before choosing a winner, determine **why** they disagree.

Common causes:

```text id="conflict02"
Agent A -> Different data
Agent B -> Different data

Agent A -> Different retrieval results
Agent B -> Different retrieval results

Agent A -> Different interpretation
Agent B -> Different interpretation

Agent A -> Different model/prompt
Agent B -> Different model/prompt

Agent A -> Hallucination
Agent B -> Correct evidence
```

So the orchestrator should inspect:

- Evidence used
- Sources
- Retrieval results
- Tool calls
- Model
- Prompt/version
- Confidence
- Timestamp/data freshness
- Business rules
- Reasoning/output trace

---

# 2. Don't Use "Agent Confidence" Alone

A common mistake is:

```text
Agent A confidence = 0.92
Agent B confidence = 0.81

Therefore A is correct.
```

❌ Not reliable.

Confidence generated by an LLM is not proof of correctness.

Instead:

```text
Correctness =
    Evidence
  + Source Quality
  + Business Rules
  + Consistency
  + Evaluation
  + Confidence
```

Confidence is **one signal**, not the final authority.

---

# 3. Evaluation Layer

Introduce a dedicated **Evaluator / Verifier**.

```text id="conflict03"
Agent A --------\
                  \
                   v
              +---------+
Agent B ------> Evaluator|
              +---------+
                   |
          +--------+--------+
          |        |        |
        A wins   B wins   Neither
```

The evaluator can use several mechanisms.

### A. Rule-based validation

For deterministic business rules:

```text
if payment_status == "PAID"
    amount_due must be 0
```

No LLM should override this.

---

### B. Evidence-based validation

Suppose:

```text
Agent A:
"Customer owes ₹10,000."

Agent B:
"Customer owes ₹7,500."
```

Evaluator checks:

```text
Billing DB
    |
    v
Outstanding balance = ₹7,500
```

Therefore:

```text
Agent B -> supported by authoritative source
Agent A -> unsupported
```

The evaluator selects B based on **evidence**, not because B "sounds better."

---

# 4. LLM-as-a-Judge

For subjective tasks, an evaluator LLM can compare the outputs.

Example:

```text
Agent A -> Test case design
Agent B -> Test case design
              |
              v
        Judge / Evaluator
```

Judge receives:

```text
Original requirement
Agent A answer
Agent B answer
Reference documents
Evaluation rubric
```

Then evaluates:

```text
Correctness
Completeness
Relevance
Grounding
Consistency
Safety
```

For example:

```text id="conflict04"
             Evaluation
                 |
      +----------+----------+
      |          |          |
 Correctness Completeness Grounding
      |          |          |
      +----------+----------+
                 |
             Score/Decision
```

NIST's current agent-evaluation work specifically describes rubric-based evaluation probes that check factual grounding against trusted corpora and produce structured verdicts and audit trails. :chatgpt-content-reference{index="1"}

---

# 5. But Don't Let the Judge Become the Single Point of Failure

This is an important **senior-level interview point**.

Don't simply build:

```text
Agent A
Agent B
   |
LLM Judge
   |
Final answer
```

because the judge can also hallucinate or have a biased evaluation.

Prefer:

```text id="conflict05"
Agent A --------\
                 |
Agent B --------+----> Evaluation
                 |        |
Reference Data --+        |
                          |
Business Rules ------------+
                          |
                    Decision Engine
                          |
                    +-----+-----+
                    |           |
                  Accept      Escalate
```

The evaluator should have **multiple independent signals**.

---

# 6. Evidence Hierarchy

A useful production hierarchy is:

```text
Highest authority
       |
       v
Business Rules / System of Record
       |
Trusted enterprise data
       |
Verified documents
       |
Retrieved knowledge
       |
Agent-generated reasoning
       |
LLM confidence
       |
       v
Lowest authority
```

For example, if an agent says:

> "The customer's balance is ₹10,000."

but the authoritative billing system says:

> ₹7,500

the agent should **not win because its confidence is 98%**.

The system of record wins.

---

# 7. What If There Is No Ground Truth?

This is where orchestration becomes harder.

Suppose two agents provide:

```text
Agent A:
"Use approach X."

Agent B:
"Use approach Y."
```

There may be no objectively correct answer.

Then evaluate according to the task's rubric:

```text
                 Decision
                    |
        +-----------+-----------+
        |           |           |
      Cost        Latency     Quality
        |           |           |
        +-----------+-----------+
                    |
                Trade-off
```

The system can return:

> "Both approaches satisfy the requirements. Approach X has lower latency, while Y provides better accuracy."

Rather than falsely declaring one universally correct.

# 9. What Does "Reconcile" Mean?

Sometimes both agents are partially correct.

Example:

```text
Agent A:
Customer has payment failure.

Agent B:
Customer's card expired.
```

These aren't necessarily contradictory.

The orchestrator can combine them:

```text
Payment failed
      +
Card expired
      =
Likely root cause
```

So the evaluator first determines whether the outputs are actually:

```text
CONTRADICTORY
```

or:

```text
COMPLEMENTARY
```

This is an important distinction.

# 10. Production Example — Your TCOE Platform

Imagine two agents analyze an ADO story.

### Agent A

```text
Story quality = HIGH
```

### Agent B

```text
Story quality = LOW
Missing acceptance criteria.
```

Don't simply ask another LLM:

> "Which agent is right?"

Instead:

```text
ADO Story
   |
   v
Quality Evaluator
   |
   +-- Check acceptance criteria
   +-- Check description
   +-- Check business rules
   +-- Check required fields
   +-- Check historical quality patterns
```

Suppose the evaluator finds:

```text
Acceptance Criteria = Missing
Business Rule = Required
```

Then:

```text
Agent B supported
Agent A rejected
```

And the trace records:

```text
Decision:
LOW

Evidence:
Acceptance criteria missing

Rule:
AC required for test generation

Agent A:
Rejected

Agent B:
Accepted
```

This creates an **auditable decision**, which is much stronger than:

> "The judge selected Agent B."

# 11. Human-in-the-Loop

For high-impact decisions:

```text
Agent A ----\
             \
Agent B ------> Evaluator
                 |
              Low confidence
                 |
                 v
             Human Review
                 |
                 v
            Final Decision
```

Examples:

- Production deployment
- Financial transaction
- Data deletion
- Security changes
- Regulatory decisions
- Customer-impacting actions

OWASP recommends human approval for high-impact actions and emphasizes that authorization should be enforced by downstream systems rather than relying on the LLM to decide whether an action is permitted. :chatgpt-content-reference{index="2"}

---

# 12. Confidence Thresholds

You can introduce thresholds:

```text
Evaluation Score >= 0.90
        |
        v
     Accept

0.70 - 0.90
        |
        v
   Re-evaluate /
   gather evidence

< 0.70
        |
        v
 Human Review
```

But these numbers should be **calibrated using evaluation data**, not arbitrarily chosen.

---

# 13. Multi-Agent Voting

For some tasks, you can use voting:

```text
Agent A -> Answer X
Agent B -> Answer X
Agent C -> Answer Y

           |
           v

        2 vs 1
           |
           v
       Answer X
```

This can work for certain classification/reasoning tasks.

But:

> **Majority does not equal truth.**

If all three agents use the same incorrect assumption, voting doesn't fix the problem.

Therefore:

```text
Voting + Evidence
```

is generally stronger than:

```text
Voting alone
```

---

# 14. Independent Verification

For important workflows, use a **Verifier Agent** that has a different role from the generators.

```text
Generator Agents
       |
       v
   Candidate
    Answers
       |
       v
+----------------+
| Verifier Agent |
+----------------+
       |
       v
Evidence + Rules
       |
       v
Decision
```

Even better:

```text
Generator -> Candidate
Verifier  -> Challenge candidate
Retriever -> Evidence
Rules     -> Deterministic validation
Human     -> High-risk approval
```

This is closer to a production evaluation architecture.

# 15. Observability Is Critical

Every decision should produce a trace.

```text id="conflict07"
trace_id
 |
 +-- user_request
 |
 +-- agent_A
 |     +-- prompt_version
 |     +-- model
 |     +-- tools
 |     +-- evidence
 |     +-- answer
 |
 +-- agent_B
 |     +-- prompt_version
 |     +-- model
 |     +-- tools
 |     +-- evidence
 |     +-- answer
 |
 +-- evaluator
 |     +-- rubric
 |     +-- evidence
 |     +-- verdict
 |
 +-- final_decision
```

This allows you to answer:

> **"Why did the system choose Agent B?"**

with actual evidence.

NIST specifically highlights the need for visibility into agent decisions, tool usage and gathered evidence, and describes machine-readable audit trails for evaluation results. :chatgpt-content-reference{index="3"}

# 16. Evaluation Metrics

For a production multi-agent system, measure:

| Metric | Purpose |
|---|---|
| Answer accuracy | Is final answer correct? |
| Groundedness | Is answer supported by evidence? |
| Agreement rate | How often agents agree? |
| Conflict rate | How often do agents disagree? |
| Resolution accuracy | Does evaluator resolve conflicts correctly? |
| False acceptance | Wrong answer accepted |
| False rejection | Correct answer rejected |
| Escalation rate | How often humans are required |
| Latency | Evaluation overhead |
| Cost | Additional model/tool calls |
| Tool accuracy | Correct tools selected |
| Safety violations | Unsafe decisions/actions |

# 18. Important Security Point

Never let an agent say:

> "My answer is correct, therefore execute it."

The agent is **not the authorization authority**.

The decision boundary should be outside the model:

```text
LLM
 |
 | proposes
 v
Policy / Evaluation Layer
 |
 | permits / rejects
 v
Tool / Business System
```

OWASP specifically recommends **complete mediation**—authorization should be enforced by downstream systems rather than delegated to the LLM. :chatgpt-content-reference{index="4"}

---

# 19. Interview-Ready Answer 🔴

If the interviewer asks:

> **"Two agents give conflicting answers. Who decides?"**

Say:

> **"I wouldn't let another LLM blindly pick one. The orchestrator sends both outputs to an evaluation layer. First I check whether they are actually contradictory or complementary. Then I compare them against authoritative evidence, deterministic business rules, and the task's evaluation rubric. For subjective tasks, I can use an LLM-as-a-Judge, preferably with structured criteria and independent evidence.**
>
> **If one answer is clearly grounded and passes the rules, I accept it. If both are valid, I reconcile them. If confidence is low or the decision is high-impact, I escalate to a human. I also record the complete trace—agent outputs, evidence, evaluation criteria, verdict and final decision—so the decision is auditable.**
>
> **The key principle is that agents generate candidate decisions; the orchestration and evaluation layer determines whether those decisions are acceptable."**

### Strong closing line

> **"I don't choose the answer based on which agent sounds more confident; I choose based on evidence, rules, evaluation, and risk."**

That is the **production-grade answer** for orchestration/evaluation.
